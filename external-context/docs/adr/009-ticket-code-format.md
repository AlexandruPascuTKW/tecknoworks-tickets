# ADR-009: Ticket codes are 10 random characters from an unambiguous alphabet

**Status:** Proposed

**Date:** 2026-11-04

**Deciders:** Alexandru Pascu (proposed); to be accepted by the development team

**Technical Story:** [`architecture.md` — Admission](../architecture.md#admission)

**Raised by:** Admission — ADM-F1 (Ticket code: "a code, in a form engineering sets"), ADM-R3 (no two
Tickets share a code), ADM-V1 (the Attendee sees it), ADM-V2 (it is printed on the Door list).

---

## Context

Every Ticket gets its own code (ADM-R3). In increment 1 the code is printed on a paper Door list, and
Front of house finds it by eye while the person at the door reads it from their phone. Increment 2
adds scanning at the door, duplicate detection and transfers, where a transferred Ticket gets a new
code and the old one stops working.

So the code has to be easy to read aloud and find on paper, impossible to guess (anyone holding a
valid code gets in), and unique across the platform.

**Constraints.** No external code service. Uniqueness is enforced by the database (a unique index in
Admission).

---

## Decision

**We have decided that a Ticket code is 10 characters drawn at random from the 31-character alphabet
`23456789ABCDEFGHJKMNPQRSTUVWXYZ`, shown in two groups of five (`K7Q2M-9XMF3`), and generated by the
`TicketCode` value object in Admission.Domain using the BCL cryptographic random number generator.**

- **Alphabet:** digits and capital letters without `0`, `O`, `1`, `I` and `L`, so no two characters
  look or sound alike.
- **Length:** 10 characters, 31¹⁰ ≈ 8 × 10¹⁴ possible codes, about 50 bits.
- **Uniqueness:** the `TicketCode` column has a unique index. If an insert ever clashes, the issuer
  draws a new code and saves again.
- **Stored** without the hyphen. Displayed and printed with it. Read case-insensitively.

---

## Rationale

1. **Readable on paper and aloud.** Short groups, no look-alike characters. That's what the
   Door list and Front of house need in increment 1.
2. **Not guessable.** With 50 random bits, guessing a valid code for a Performance of a few hundred
   Tickets is negligible, so a made-up code won't get anyone in.
3. **Unique by construction and by database.** A clash is astronomically rare, and the unique index
   catches it anyway.
4. **Ready for scanning.** Increment 2's QR codes can encode the same string. Transfers just draw a
   new one.

---

## Alternatives Considered

### Alternative 1: A GUID

**Pros:** unique without thinking; no index clash handling.
**Cons:** 36 characters, unreadable on a printed list or over a noisy door.
**Why Rejected:** fails the paper Door list.

### Alternative 2: A sequential number per Performance

**Pros:** shortest; easy to sort on the list.
**Cons:** guessable: knowing ticket 104 means 105 exists, and anyone can walk in with it.
**Why Rejected:** a guessable code is a free ticket.

### Alternative 3: A code signed with a secret (HMAC)

**Pros:** could be checked offline without the database.
**Cons:** longer codes; key management; offline checking isn't needed until a scanning design asks
for it.
**Why Rejected:** solves a problem increment 2 hasn't specified yet.

---

## Consequences

### Positive Consequences

- ✅ Readable, unguessable, unique codes on My tickets and the Door list (SC-ADM-002).
- ✅ No coordination service; generation is local to Admission.

### Negative Consequences

- ⚠️ **10 characters is long to type** if door staff ever key codes in by hand. Increment 2's
  scanning makes that rare.

### Neutral/Unknown Consequences

- 🤷 Increment 2 may want offline scanning; revisit Alternative 3 then.
