# Templates

Skeleton for a new domain spec. The worked example — a complete small spec in this format — is
`assets/example/specs/LND/lending.md`, with its project config in `assets/example/spec-config.json`.

## Spec — `<specs_root>/<DOMAIN>/<name>.md`

```markdown
# <Domain title>

## Contents

- [Context](#context)
- [Glossary](#glossary)
  - [Core](#core)
  - [People and roles](#people-and-roles)
  - [Owned by other specs](#owned-by-other-specs)
- [Use Cases](#use-cases)
  - [<Stage>](#<stage-slug>)
    - [LND-A1 — <Action>](#lnd-a1--<action-slug>)
    - [LND-V1 — <View>](#lnd-v1--<view-slug>)
- [Fields](#fields)
  - [<Concept>](#<concept-slug>)
- [Domain Rules](#domain-rules)
  - [<Group>](#<group-slug>)

## Context

<Who has the problem, what the real situation is, where this domain starts and ends, and the
principles everything below follows from.>

## Glossary

### Core

| Term | Definition |
|------|-----------|
| **<Term>** (<short form>) | <What it means here. No rules.> |

### People and roles

| Term | Definition |
|------|-----------|
| **<Role>** | <What this person does in the domain> |

### Owned by other specs

| Term | Definition |
|------|-----------|
| **<Term>** | Owned by <the owning spec and its code>. <What this domain does with it> |

## Use Cases

Each use case is either an **action** — something a person does that changes the domain — or a
**view** — something a person looks up. Who can lists everyone allowed; anyone not listed cannot.
Every action and view applies only within the user's scope (LND-R1). Each entry's **Status** is
🟢 Built, 🟡 Partly built (with a **Gaps** line naming the rules or fields not yet met, and a
**To reach 🟢** line saying what has to change) or 🔴 Not
built. *❓ Needs PO clarification* marks something the product owner has not yet clarified;
**⛔ Blocker** marks the few open points that shape the foundation of the build, where a wrong
answer would mean reworking it.

### <Stage>

<One line: what this stage of the domain is for.>

#### LND-A1 — <Action>

<What it does, in one sentence. No steps, no screens.>

- **Who can:** <Roles>
- **Input:** <a whole concept — "a Hold" — or field names: "Title (required), Pickup branch">
- **Rules:** LND-R1, LND-R2
- **Status:** 🔴 Not built
<!-- 🟡 Partly built adds, right under Status:  - **Gaps:** LND-R2
                                              - **To reach 🟢:** <one line, business words, no code> -->

#### LND-V1 — <View>

<What someone finds out, and why.>

- **Who can:** <Roles>
- **Returns:** <a whole concept or field names, and any derived value, e.g. a Loan's status>
- **Can filter by:** <filters, if any>
- **Rules:** LND-R3
- **Status:** 🔴 Not built

## Fields

<One line: every field an action takes or a view returns, defined once; requiredness lives on
each action's Input, the rules that span fields, and each concept's own sentence.>

### <Concept, as the Glossary names it>

<What the concept always has, in one sentence — or "Not a concept: …" for a plain group.>

| ID | Field | Allowed values and validation | Source column |
|----|-------|-------------------------------|---------------|
| **LND-F1** | <Field> | <What makes a value valid> | <column in the import or export, or —> |

<!-- The Source column is optional: keep it only when values arrive from a source with its own
column names, such as an import template. -->

## Domain Rules

### <Group>

**LND-R1 — <Title>.** <The rule.>

**LND-R2 — <Title>.** <The rule.>
*[❓ Needs PO clarification — <a direct question>? <What the working answer was inferred from.>]*
```

Replace `LND` with your spec's domain code. GitHub anchors: lowercase, punctuation (including `—`
and commas) dropped, spaces to hyphens — so `LND-A1 — Lend an Item` becomes `#lnd-a1--lend-an-item`.
The Contents list is generated by `scripts/build_toc.py`, so you never write these by hand.

## Project config — `spec-config.json` (optional)

Put it at the root the specs share; the scripts find it by walking up from the spec. Every key is
optional, and paths are relative to the file's folder. See `assets/example/spec-config.json`.

| Key | Default | What it does |
|-----|---------|--------------|
| `specs_root` | `"specs"` | Where specs live |
| `scenarios_root` | `"scenarios"` | Where scenario files live, mirroring `specs_root` (`specs/LND/lending.md` → `scenarios/LND/lending.md`) |
| `index_files` | `[]` | READMEs or indexes searched for IDs the spec no longer defines (KI-8) |
| `roles` | from the glossary | Role names for the "permission outside *Who can*" lead (KI-6). Without it, the terms of the glossary group whose heading says "role" or "people" |
| `role_implies` | `{}` | `{"Librarian": "Branch Manager"}` — an entry listing the first must list the second (KI-12) |
| `cross_spec_id_pattern` | `\b[A-Z]{2,5}-\d{3}\b` | How another spec is cited (`MEM-001`); an *Input* naming one is that spec's concept, not a field here |
| `forbidden_paths` | `[]` | Paths or sources a spec must never cite (the audience rule) |
| `rules_line_max` | `12` | A *Rules* line longer than this is a KI-19 lead |
| `use_case_letters` | `{"action": "A", "view": "V"}` | The letters in action and view IDs (`LND-A1`, `LND-V1`). A project already numbered with other letters keeps them without renumbering — `{"action": "C", "view": "Q"}`. Each is one capital letter, not R or F, and the two differ |
| `label_sources` | `[]` | Folders `sdlc-scenario-manager`'s `check_labels.py` searches for the labels scenarios quote |
