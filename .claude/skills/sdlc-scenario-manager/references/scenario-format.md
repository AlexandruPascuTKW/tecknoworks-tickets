# Scenario format

Shared conventions — ID formats (`LND-A/V/R/F…`), the 🟢 Built / 🔴 Not built status and section
headings — are owned by `sdlc-spec-manager` (its `references/spec-format.md`); follow them, don't
restate them here.

A scenario is an acceptance check and a manual test in one: concrete steps a product owner can
read, a tester can follow cold and an agent can automate, proving that the product does what the
spec says. The spec says what must be true; the scenario says what you do, and what you see, to
find out.

Every example below comes from the worked example,
`../sdlc-spec-manager/assets/example/scenarios/LND/lending.md` — scenarios for the library lending
spec beside it. Read the two side by side.

## What gets a scenario

Three questions get mixed up when people talk about tests: what a good scenario looks like, which
behaviours deserve one, and how — at which level, with which tools — the team proves the rest. This
skill answers the first two. The third is the team's call; nothing here assumes a test strategy.

**Start from the main journey.** Each spec has one end-to-end *spine* scenario walking what people
most often do from start to finish — for Lending, an Item lent, renewed and returned. It is filed
under the action it ends on and lists every action and view it passes through. The spine shows
the hand-offs between actions hold together, which scenarios for single actions never do.

**Then add a scenario for each behaviour a user or the business would notice if it broke** — a
refusal that protects money or a person's data, a queue that must be fair, something recorded that
someone will later rely on, a permission that keeps one role out of another's decisions. In the
example: a returned Item going to the first Member waiting (SC-LND-002), a Renewal refused while
someone waits (SC-LND-003), a Librarian unable to waive a Fine (SC-LND-004). A permission worth a
scenario gets a *negative* one: someone who may not, can't.

**Every scenario earns its place.** Each one is read by the product owner, kept in step with a
product that keeps changing, and run again on every release — so each is an ongoing cost, paid for
by the confidence it gives. Before adding one, ask:

- Would a user or the business notice, and care, if this broke? If not, it doesn't need a scenario.
- Does another scenario already prove it — would both fail for the same reason? Then keep one.
  Don't keep short scenarios that only repeat part of the spine.
- Is it detail inside a behaviour (a value range, a format, a message's wording) rather than the
  behaviour itself? Detail rarely earns a scenario of its own.

A spec stays complete either way: a rule without a scenario isn't a gap, it's a decision. A file
that grows a scenario per rule is a sign detail is creeping in — prune it rather than maintain it.

## Where the steps come from

The spec is required — or, without one, the acceptance criteria (see
[Without a spec](#without-a-spec)); the steps' labels come from the **product** — a running app, a prototype or
a design. Look labels up there (or run `scripts/check_labels.py`) rather than guessing.

| You have | Then |
|----------|------|
| The spec and a running app | The best case: you can write steps you know work |
| The spec and a prototype or design | Take control names, labels and wording from it — never layout, classes or component names |
| Steps someone describes | A good start, already in the right shape; check them against the spec and the product's labels |
| Only the spec | Write the steps anyway against the labels you expect, and list them as assumed labels in your report |

**When the product contradicts the spec, that is a finding, not a step.** Write the steps the spec
requires and report the contradiction — to the spec (`sdlc-spec-manager`) if the rule is wrong, or
as a bug if the product is. Writing steps that match whatever was built turns the scenario into a
transcript of it. Findings go in your report or the pull request, never in the scenario file.

## File layout

A scenario file mirrors its spec's path: `specs/LND/lending.md` →
`scenarios/LND/lending.md`. Projects with other folders set `specs_root` and `scenarios_root` in
`spec-config.json` (see the spec manager's `references/templates.md`); the scripts follow them.

1. `# Scenarios: <spec title>`
2. `> Spec: [path](../../specs/<DOMAIN>/<name>.md) · Last reviewed: YYYY-MM-DD`
3. `## Contents` — generated by the spec manager's `build_toc.py`: Test data, each use-case section,
   and each scenario under it with its 🟢/🔴 status.
4. `## Test data` — see below.
5. One `## LND-An — Title` (or `## LND-Vn — Title`) section per action or view that has a
   scenario, matching the spec's heading text exactly, each holding its scenarios as
   `### SC-<DOM>-NNN — what is proven`.

Scenario IDs are `SC-<DOMAIN code>-<NNN>` (e.g. `SC-LND-003`), never reused once the file is
committed; before the first commit, renumber freely after cutting scenarios. A scenario proving
several actions sits under the first and lists all of them in its header.

The title says what is **proven**, not what is done: "A Librarian cannot waive a Fine", not "Test
the Fines tab".

`scenarios/README.md` holds the index, the "what gets a scenario" policy, the ID conventions and the
status legend — nothing else (see `references/templates.md`).

## Test data

Describe the data each scenario needs by the **part it plays**, not by real names — any environment
with that shape can run the file, whatever its records are called.

```markdown
## Test data

Scenarios refer to data by the part it plays, not by name — any environment with this shape will
do. Where a step says "any", the choice does not affect the outcome.

| Placeholder | What it must be |
|-------------|-----------------|
| **Librarian 1** | A Librarian at Branch North |
| **Member 1** | A Member in good standing, with no Loans, Holds or Fines |
| **Item 3**, **Member 4** | Item 3 is a book on an *Active* Loan to Member 4 from Branch North, renewed fewer than twice, whose Title has a *Waiting* Hold by any other Member |
```

- **No real names** — not of people, branches, customers or records. A placeholder by role keeps
  real data out of a file others read, and keeps the scenario runnable in any environment.
- **Don't name placeholders so they look like IDs** — "Member R2" or "Item LND-4" reads as a rule
  or entry to people and to the checker. Use numbers or plain words: "Member 1", "Branch North".
- **Constrain what decides the outcome.** "renewed fewer than twice" in the row above keeps the
  renewal limit from refusing the Renewal for the wrong reason.
- **Say "any" in steps where the choice doesn't matter** ("enter any reason"), and use a
  placeholder only where it does. Keep the table to what the scenarios actually use.
- **A scenario that changes a record gets its own record**, so no scenario's result depends on
  which ran first.

## Scenario header

A bullet list — plain consecutive lines merge into one paragraph when rendered:

```markdown
### SC-LND-003 — A Loan is not renewed while another Member is waiting for its Title

- **Covers:** LND-R10
- **Use cases:** LND-A3, LND-V1
- **Status:** 🟢 Built
- **Setup:** sign in as Librarian 1, at Branch North
- **PO Feedback:** none yet
```

- **Covers** — only the rules this scenario genuinely proves, plus the action or view whose *Who can*
  it proves when it tests a permission (`Covers: LND-A7` for "a Librarian cannot waive a Fine").
  Citing a rule the steps never exercise is false coverage.
- **Use cases** — the actions and views it walks through, the primary one first. (Older files call
  this line *Commands*; the checker reads both.)
- **Status** — 🟢 Built or 🔴 Not built, as defined in the spec manager's `spec-format.md`. Only
  these two: a scenario either passes or it doesn't, even when an action is 🟡 Partly built.
  `sdlc-build-status` judges it against the product.
- **Setup** — who is acting, in what role, and anything that must already be true.
- **PO Feedback** — what the product owner said about this scenario, with the date:
  `PO Feedback: "<their comment>" (YYYY-MM-DD)`. Write `none yet` until they have reviewed it.
  Record their words, not our reading of them; if the feedback changes a rule, fold it into the spec
  with `sdlc-spec-manager` and then update the steps.
- No Priority line, no "Pending because" line, no Data line duplicating the Test data table.

## Steps

```markdown
1. On the "Loan desk", enter Member 4's card number in "Member card" and click "Find member"
2. Click the "Loans" tab
   - → Item 3 is listed as "Active"; note its Due date and Renewals
3. Click "Renew" on Item 3
   - → "Renewal refused: another member is waiting for this title"
   - → Item 3's Due date and Renewals are unchanged
```

- **One action per step**, numbered. Each result is an indented sub-bullet starting `- →`, so it
  renders on its own line. "Enter a card number and click Find" is fine as one step; three actions
  are not.
- **Name the real control**, in quotes, exactly as the product labels it. A vague verb ("take the
  Item back", "look at the history") can't be followed. Run `scripts/check_labels.py` on the file:
  every quoted label it can't find is either an assumed label (say so in your report) or a mistake
  (fix it).
- **Assert what you would observe** — what's shown, listed, refused, recorded. Never narrate the
  rule back ("because a Hold queue blocks renewals…"); the `Covers` line links to it.
- **End on the result that proves the rule**, and where it matters, what must *not* have changed.
- **Refusals: also check the other way in.** For a permission or a refusal, a hidden button isn't
  enough — add a plain step asking the tester to check the system refuses it when tried another
  way:
  ```markdown
  3. Try to waive Fine 1 as Librarian 1 another way than the screen — a saved link, or a direct
     request to the system
     - → refused
     - → Fine 1 is still "Outstanding"
  ```
  How to try it is up to whoever runs it; the step only says what must hold.
- **No selectors, endpoints, waits or status codes** — the people reading the file don't need them,
  and whoever automates it adds them.
- **Every scenario has steps.** Don't leave a scenario as a one-line intent because no control
  exists yet — write the steps against the label you expect and report it as assumed. An
  intent-only scenario can't be run, reviewed or automated.
- **Scenarios are independent.** A scenario never relies on another having run; whatever it needs
  is in Setup and Test data, written as a state ("Member 5 owes Fine 1"), not as history ("has just
  been fined").

## Journeys across specs

Some journeys cross specs — a Member pays a Fine in Payments, then can borrow again here. One
scenario for the journey proves the seam: that what one spec hands to the next survives. Put it in
the scenario file of the spec where the journey ends, cite only that spec's IDs on Covers and
Use cases (the checker reads them against that spec), and name the other spec's part in plain words
in the steps. Don't re-prove rules the other spec's scenarios already prove.

## Without a spec

A product owner or tester may hand over acceptance criteria, a ticket, a user story or a plain
description instead of a spec — a Jira ticket, Given/When/Then, a paragraph in a chat. Read it as
given; don't ask for it to be reformatted. The scenarios come out in the same format, held to the
same bar: everything above applies in full — the spine first where there is a journey, one scenario
per behaviour a user or the business would notice, no two proving the same thing.

**Acceptance criteria are the input, not part of the file.** Don't copy them in or give them a
section: a criterion says what must be true, a scenario shows it with a concrete case, and a copy
would drift from the ticket the day either changes.

**Where the file goes.** Wherever the team likes — `scenarios/borrowing-with-fines.md` for a
feature, say. There is no spec path to mirror.

**Header.** The file names its source where a spec-based file links its spec:

```markdown
# Scenarios: Borrowing with Fines

> Source: [JIRA-412](https://…/browse/JIRA-412) · Last reviewed: YYYY-MM-DD
```

or `> Source: described by the product owner on YYYY-MM-DD` when it came in conversation. Group
scenarios under `##` headings in plain words for the parts of the feature ("## Lending an Item"),
since there are no action or view headings to file them under.

**Scenario IDs** are still `SC-<CODE>-NNN`, with a short code the team picks for the feature
(`SC-BRW-001` for borrowing). **No `Use cases:` line** — there are no action or view IDs to list.

**Covers** points to the rule the scenario proves, in one of two forms; the team picks one and
keeps to it:

- **The rule in a few plain words** — `Covers: a Member with an unpaid Fine can't borrow`.
  Recommended when nothing else records the rules: read down the file's Covers lines and you have
  the list of rules. A short ticket in brackets after the words is fine:
  `Covers: a Member with an unpaid Fine can't borrow (JIRA-412)`.
- **Just the ticket** — `Covers: JIRA-412`, when the ticket stays the source of truth for the
  rules.

**Gaps.** Where the criteria leave something open — who may do it, what happens at the edge, what
the user sees — mark that step or Setup `*[❓ Needs PO clarification — …]*` and put the question
to the product owner. Never invent the behaviour: a guessed rule in a scenario reads exactly like an
agreed one.

**One wording per rule.** Without a spec, a rule lives only in its scenarios, so two scenarios can
state it differently — "an unpaid Fine blocks borrowing" in one, "a Fine over €5 blocks borrowing"
in another — and nobody can say which is right. When a rule appears twice, use the same words.

**Status** is still 🟢 Built or 🔴 Not built; `sdlc-build-status` judges it from the Setup, each
`→` result and the Covers statement, with no spec IDs to cite.

**Checks.** `build_toc.py` and `check_labels.py` work as usual. `check_refs.py` reads a spec, so it
doesn't apply.

**Later, a spec.** When the team wants one, `sdlc-spec-manager` can start it from these files: each
plain-words Covers line becomes a domain rule with an ID. The scenarios then cite the new IDs on
Covers, gain a `Use cases:` line, and the file moves to mirror the spec's path. Their `SC-` IDs stay as they are: an ID is never renumbered, and tickets or tests may already cite it.

## Leave out

These were tried and removed as noise — don't reintroduce them:

- a coverage table (each scenario's `Covers`/`Use cases` and the Contents already carry it);
- tables of rules without scenarios, findings, or product contradictions (report those instead);
- a "verification status" paragraph (the Status line says it);
- placeholder README sections — empty rule-gap tables, "not yet decided" rows, verdict columns.
