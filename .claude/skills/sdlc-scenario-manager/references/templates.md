# Templates

Skeletons for a new scenario file — with or without a spec — and the scenarios README. The worked
example is `../sdlc-spec-manager/assets/example/scenarios/LND/lending.md`, beside the spec it
proves.

## Scenario file — `<scenarios_root>/<DOMAIN>/<same name as the spec>.md`

```markdown
# Scenarios: <Spec title>

> Spec: [`specs/<DOMAIN>/<name>.md`](../../specs/<DOMAIN>/<name>.md) · Last reviewed: YYYY-MM-DD

## Contents

<generated by the spec manager's build_toc.py>

## Test data

Scenarios refer to data by the part it plays, not by name — any environment with this shape will
do. Where a step says "any", the choice does not affect the outcome.

| Placeholder | What it must be |
|-------------|-----------------|
| **<Placeholder>** | <Shape it must have> |

---

## LND-A1 — <Action or view, exactly as the spec's heading>

### SC-LND-001 — <What is proven>

- **Covers:** LND-R1
- **Use cases:** LND-A1
- **Status:** 🔴 Not built
- **Setup:** sign in as <placeholder>, at <placeholder>
- **PO Feedback:** none yet

1. <One action, naming the real control in quotes>
   - → <what you then observe>
2. <Next action>
   - → <the result that proves the rule>
```

Replace `LND` with the spec's domain code. Write `## Contents` with nothing under it and run
`build_toc.py` to fill it.

## Scenario file without a spec — wherever the team likes, e.g. `scenarios/<feature>.md`

Written from acceptance criteria, a ticket or a story (see `scenario-format.md`, Without a spec).
The criteria themselves are not copied in.

```markdown
# Scenarios: <Feature>

> Source: [<TICKET-ID>](<ticket link>) · Last reviewed: YYYY-MM-DD

## Contents

<generated by the spec manager's build_toc.py>

## Test data

Scenarios refer to data by the part it plays, not by name — any environment with this shape will
do. Where a step says "any", the choice does not affect the outcome.

| Placeholder | What it must be |
|-------------|-----------------|
| **<Placeholder>** | <Shape it must have> |

---

## <Part of the feature, in plain words>

### SC-<CODE>-001 — <What is proven>

- **Covers:** <the rule in a few plain words> (<TICKET-ID>)
- **Status:** 🔴 Not built
- **Setup:** sign in as <placeholder>, at <placeholder>
- **PO Feedback:** none yet

1. <One action, naming the real control in quotes>
   - → <what you then observe>
2. <Next action>
   - → <the result that proves the rule>
```

`<CODE>` is a short code the team picks for the feature (`BRW` for borrowing). With no ticket,
write the source as `> Source: described by <role> on YYYY-MM-DD`; if the team keeps the ticket as
the source of truth for the rules, `Covers:` is just the ticket ID. There is no `Use cases:` line.

## `scenarios/README.md` — create once, then only add index rows

```markdown
# Scenarios

> Acceptance scenarios for <Project>: step-by-step behaviour the product owner can read, a tester
> can run and an agent can automate.
>
> Specs: [`/specs/`](../specs/) — what each domain *is*.
> These files — what proves it behaves that way. One scenario file per spec file, at the same path
> under `scenarios/`.

## Index

| File | Spec | Actions and views with scenarios | Scenarios |
|------|------|----------------------------------|-----------|

## What gets a scenario

- **One end-to-end spine** per spec walks its main journey, filed under the action it ends on.
- **One scenario for each behaviour a user or the business would notice if it broke.** A
  permission worth a scenario gets a negative one: someone who may not, can't.
- **Every scenario earns its place:** no two prove the same thing, and each is kept in step with the
  product as it changes. A rule without a scenario is a decision, not a gap.

## Project Conventions

| Convention | This project |
|------------|--------------|
| **IDs** | Owned by the specs: `<DOM>-A`, `-V`, `-R`, `-F` — unique across the project, never reused |
| **Use-case link** | Each scenario lists the actions and views it walks through on its Use cases line, primary first, and sits under the first one's heading. A permission it proves is cited as that action or view on Covers |
| **Scenario IDs** | `SC-<DOMAIN>-<NNN>`, e.g. `SC-LND-001`. Never reused |
| **Control naming** | Steps name controls by their visible label, taken from the product; until it has the control, the label is assumed and `check_labels.py` lists it |

## Status Legend

| | Status | Meaning |
|---|---|---|
| 🟢 | **Built** | Implemented; the scenario must pass |
| 🔴 | **Not built** | Not implemented yet; its steps may already be written |
```

When a scenario is added or removed, update the README index row's counts. A withdrawn scenario is
struck through with a date and reason, and its ID is never reused.

## Label sources — `label_sources` in `spec-config.json`

`scripts/check_labels.py` needs to know where the product's labels live. Pass `--src PATH` (repeat
it for several), or list the folders once in the project's `spec-config.json` — the same file the
spec manager's scripts read, found by walking up from the scenario file:

```json
{
  "specs_root": "specs",
  "scenarios_root": "scenarios",
  "label_sources": ["../web/src", "../web/public/locales"]
}
```

Paths are relative to the config's folder. Any front end that keeps its words in source or resource
files works: React or Vue components, HTML, Razor views, translation JSON or `.resx`. Pick the
extensions with `--ext` if the default list misses yours.
